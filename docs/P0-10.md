# P0-10 Runtime Event / Reconciliation

## Runtime Event Summary

P0-10 separates external runtime facts from internal Execution truth. n8n,
Agent Runtime and Artifact Store adapters emit a normalized `RuntimeEvent`;
the event is persisted, transformed into a `RuntimeObservation`, and then
processed by `ReconciliationService`. No source adapter assigns Execution or
Node state directly. P0-10 uses Fake n8n, Agent and MinIO facts Ports; real
runtime integration remains TBD-04.

## Event Model

`RuntimeEvent` contains event_id, source, event_type, tenant_id,
correlation_id, execution_id, node_id, attempt_no, external_reference,
occurred_at, received_at, payload_hash, version and processing state. Payloads
are recursively redacted before persistence. Processing states are
`RECEIVED`, `NORMALIZED`, `PROCESSED`, `IGNORED`, and `FAILED_PROCESSING`.

## Observation Model

`RuntimeObservation` is the normalized external fact with observation_id,
event_id, execution/node/attempt identity, observed_state, source, confidence,
occurred_at and safe evidence. One event can produce at most one observation
for a normalized state.

## Adapter Design and Normalization

`N8nRuntimeAdapter`, `AgentRuntimeAdapter`, and `ArtifactRuntimeAdapter`
translate source vocabulary such as `success`, `completed`, and `validated`
into canonical states. Artifact adapters emit events from Artifact lifecycle
metadata. A polling adapter may return RuntimeEvents, but it must use the same
receive/normalize/reconcile pipeline.

## Reconciliation Rules

`POST /api/v1/executions/{id}/reconcile` reads one fact set from each source
Port and deterministically returns exactly one of `MATCHED`, `EVENT_MISSING`,
`STALLED`, `ARTIFACT_MISMATCH`, or `UNCERTAIN`. The response retains both
source evidence and sanitized raw facts; it does not evaluate quality or
write CMM state.

- Agent or n8n success never alone makes a Node successful.
- Required Artifact validation PASS and object existence are required for a
  successful output Node.
- Agent failure, engine failure, or Artifact INVALID has failure precedence.
- Terminal success is not overwritten by a delayed RUNNING observation.
- Execution succeeds only after a workflow success observation and every Node
  is reconciled successfully.
- Execution/Node transitions go through `StateTransitionService`; adapters do
  not update status columns.

## Persistence / Migration

Migration `0009_runtime_event_reconciliation` extends the legacy runtime_event
record with tenant/source/correlation/hash/processing fields and adds
`runtime_observation`, tenant-scoped indexes, event uniqueness, execution
tenant FK, and explicit down migration. Existing `0001` through `0008` files
are unchanged.

## API Changes

`POST /api/v1/runtime-events` receives and persists an event only. Duplicate
replays are idempotent by `event_id`; evaluator/quality fields are rejected,
including nested payload keys. The adapter normalizes aliases before storage.
`GET /api/v1/executions/{id}/runtime-events` returns tenant-scoped event
processing facts and normalized observations; it never returns external object
content. `POST /api/v1/executions/{id}/reconcile` returns the five-state result
and retained evidence.

## Security and Tenant Isolation

Sensitive payload values are redacted (`password`, `token`, `api_key`, private
key, authorization and credential values). Queries require tenant scope.
Execution tenant and correlation lineage are checked before event acceptance.

## Tests and Proofs

- Proof A: `test_proof_a_duplicate_event_creates_one_observation` submits the
  same event twice and observes one persisted event and one Observation.
- Proof B: `test_proof_b_out_of_order_success_then_running_does_not_regress`
  proves late RUNNING does not overwrite Node SUCCEEDED.
- Proof C: `test_proof_c_multi_source_artifact_invalid_wins` combines Agent
  success, n8n success and Artifact INVALID; the Node remains failed.

P0-10 tests (18 total, including the PostgreSQL suite) cover the four fault
injection scenarios, planning-blueprint.v3 compatibility, Artifact dependency,
event retry versus Business Attempt retry, tenant isolation, correlation,
PostgreSQL constraints/indexes, concurrent idempotency, transaction rollback,
and migration rollback.

## Boundaries

P1 Checkpoint Recovery, Resume Root, trusted Checkpoint, input fingerprint,
recovery lineage, Evaluation, FIELD_MAPPING and Artifact Intelligence are not
implemented.
