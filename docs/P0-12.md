# P0-12 P0 E2E 闭环验收

P0-12 是验收编排层，不新增产品状态、外部协议或运行时行为。它使用
P0-03～P0-11 已接受的 Fake ports，将 INT-01B 的 `planning-blueprint.v3`
形态串成一条可重复的闭环：

`plan -> snapshot -> IR -> S0~S4 -> publish -> execute -> runtime events -> SUCCEEDED -> ArtifactRef -> CMM outbox SENT`

## 确定性证据

`tests/p0_12/p0_e2e_acceptance.py` 中的 `P0E2EAcceptance` 收集固定的 tenant、correlation、
execution、artifact identity、runtime event 原始证据和 CMM outbox 状态。验证层只调用
已有 `CompositionFixture`、`ExecutionController`、`RuntimeEventService`、Artifact
Manager、`ContextEventService` 和 Fake adapters。

## 故障注入

门禁覆盖六个已编号场景：Blueprint/Execute replay、Publish/Execute response loss、
Runtime Event duplicate/missing、Agent stalled、Artifact hash mismatch、CMM disconnect
和 Publisher crash recovery。CMM 断开只将 outbox 保留为 `PENDING` 并报告 degraded，
S0~S4 自测门禁仍必须通过。每个场景在 `tests/p0_12/test_p0_e2e.py` 有独立断言。

## 边界与缺口

不实现真实 MinIO/n8n 联调（TBD-04）、CMM 服务端/TBD-03 正式字段、P1 Checkpoint
Recovery、P2 Memory Summary 或新的产品 API。migration up/down 和历史 P0-02～P0-11
回归由 `scripts/check-p0-12.sh` 委托现有门禁完成。PostgreSQL 使用
`tests/p0_12/test_postgres_e2e.py` 的隔离 schema；没有 DSN 时脚本明确返回
`P0_BLOCKED`，不会把 skipped 当作 PASS。真实外部 E2E 只有配置经批准的命令后才执行，
否则报告为 `BLOCKED_EXTERNAL`。

运行：

```bash
P0_12_POSTGRES_DSN="$POSTGRES_DSN" bash scripts/check-p0-12.sh
```

本次已使用现有 `pg-fresh` PostgreSQL 16.13 容器完成 full 门禁：migration 1～11
up、migration 11 down、P0-02～P0-11 历史回归及 P0-12 PostgreSQL 专项均通过，
测试只创建并清理隔离 schema，不修改既有业务 schema。真实 n8n/Agent/MinIO/CMM
仍需通过批准的 `P0_12_EXTERNAL_E2E_CMD` 单独执行。

## 真实外部调试证据

重启后已恢复并检查真实服务：n8n `GET /healthz`、Word Agent
`GET http://127.0.0.1:4324/health`、Report Agent
`GET http://127.0.0.1:6000/api/health`、gateway `/health` 和 MinIO
`/minio/health/live` 均返回成功。使用现有 n8n gateway adapter 创建了唯一隔离
smoke workflow，执行 `validate -> inactive import -> canary -> activate -> webhook`
后，真实 PostgreSQL `execution_entity` 记录为 `id=6,status=success`；随后 workflow
已 retire，n8n 恢复健康。真实 MinIO Adapter 在隔离 bucket/prefix 中完成 put、
metadata/stat、hash/schema validation 和 delete，清理后对象不存在。

调试还发现 gateway 的 psql 参数占位符在当前 n8n PostgreSQL 容器组合中未展开，
已在 `scripts/orchestrator_gateway_dev.py` 对经过严格 workflow-id 校验的值采用安全
字面量查询，并通过真实 webhook execution 复验。上述 smoke 只证明外部边界和 n8n
执行能力，不等同于真实业务 Agent 输出、Artifact 注册、Runtime reconciliation
和 CMM 投递的完整闭环；因此封版报告仍保持 `BLOCKED_EXTERNAL`。

离线诊断模式：

```bash
P0_12_MODE=offline bash scripts/check-p0-12.sh
```

脚本会执行既有离线质量门禁、完整离线回归和 Fake P0-12 测试，但因 PostgreSQL
未验证且真实外部联调未执行而返回 `P0_BLOCKED`（外部状态为
`BLOCKED_EXTERNAL`）。JSON 默认写入 `/tmp/p0-12-acceptance.json`，Markdown 默认写入
`P0-12-ACCEPTANCE-REPORT.md`；两者都可通过环境变量覆盖。

`execution-orchestrator-wf-8eb70076d32dd8418754a847-v1`，打开后确认 Active，点击
`Execute Workflow`/`Test workflow`，从 `orchestrator::manual-start` 开始执行。该路径不依赖
Webhook；当前实例的 Webhook credential 仍需单独配置后才能使用自动 HTTP trigger。
