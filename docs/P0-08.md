# P0-08 Execution / Node / Attempt

## Scope

P0-08 adds the formal production execution control plane. A formal run can
only use a `PUBLISHED` Workflow Version with the completed P0-07 publish
record. Self-Test Canary runs remain outside this controller and use the
`SELF_TEST` path owned by P0-07.

## ExecutionController ownership

`ExecutionController` resolves the single P0-07 formal execution reference,
loads the immutable runtime definition, creates or replays the authoritative
Execution, invokes `WorkflowEnginePort` through `WorkflowReleaseService`, and
binds the external execution reference. It never looks up a newer Workflow
Version or Registry Snapshot after creation.

The persisted identity is:

`tenant_id + workflow_family_id + workflow_version + client_request_id`

The Execution ID and engine operation key are deterministic hashes of this
identity. `Idempotency-Key` is required at the API boundary and is scoped by
tenant, operation, Workflow identity, and stable client request identity; the
business identity remains stable across an HTTP retry with a changed transport
key. Different request content under the same business identity produces an
`ExecutionIdempotencyConflict`.

## Runtime identity and tenant boundary

`X-Tenant-Id` is an Auth/TenantContext seam pending TBD-08 authentication. It
is not treated as a complete authentication protocol. PostgreSQL verifies that
the tenant owns the Workflow Family before creating an Execution. The runtime
envelope carries tenant, correlation, Workflow, Execution, node, attempt, and
stable invocation identity.

## Node and Attempt semantics

One logical `NodeExecution` exists per `(execution_id, node_id)` and the node
must come from the frozen per-Execution runtime definition. A Business Attempt
uses `(execution_id, node_id, attempt_no)` and is created only by explicit
business re-execution. `current_attempt` is updated in the same transaction as
Attempt creation and has a deferred foreign key to the Attempt row.

Technical retry is represented by:

`RUNNING -> RETRY_WAIT -> RUNNING`

within the same Attempt. Only `retry_count`, retry evidence, error code and
retry timing metadata change. Exhaustion marks that Attempt, Node and (when
configured by the current operation) Execution as `FAILED`; it never creates a
new Attempt automatically. Retry limits, backoff and timeout are supplied by
the persisted IR policy and remain TBD-06 configuration.

## Engine idempotency and crash window

`WorkflowReleaseService` remains the only formal execute gate. The engine
operation key is derived from the stable Execution ID. The Fake engine and
adapter contract prove that a successful external side effect followed by a
lost local response is replayed to the same external execution. Live n8n
conformance remains TBD-04.

## Ports and seams

- `ExecutionRepositoryPort`: transactional Execution, Node, Attempt facts.
- `WorkflowEnginePort`: external validate/import/publish/execute boundary from
  P0-06.
- `RuntimeObservationConsumerPort`: future normalized runtime facts; no HTTP
  runtime-event ingestion or reconciliation is implemented here.
- `CheckpointReferencePort`: reference-only seam; trusted checkpoint and input
  fingerprint algorithms remain P1-01.
- PATCH/REPLAN are explicit Execution state decisions only. Version lineage,
  recovery, evaluation, Artifact/MinIO and reconciliation remain later scope.

## Persistence

Migration `0005_execution_control` adds immutable runtime definitions and
per-Execution node definitions, frozen Execution identity fields, engine
references, retry metadata, current Attempt linkage, tenant/correlation indexes,
and database guards. It supports explicit up/down and preserves migrations
0001 through 0004.

No secret values are persisted. Runtime inputs are recursively checked for
passwords, API keys, tokens, authorization material, private keys and bearer
values; only opaque `credential_ref` values are allowed.

## Verification

The P0-08 unit/API suite covers formal execute gates, idempotent replay and
conflict, lost engine responses, tenant isolation, secret rejection, node
transitions, retry exhaustion, PATCH/REPLAN boundaries, and the two required
Attempt proofs. PostgreSQL integration covers migration up/down, persistence,
tenant enforcement, concurrent Execution/Attempt creation, transaction
rollback, and engine-reference crash recovery. Ruff/Mypy are optional and were
not available in the offline environment; deterministic AST lint/type gates
are the reported quality gates.
